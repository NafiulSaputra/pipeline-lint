# DE005 `driver-collect`

**Severity:** warning · **Languages:** PySpark, Databricks notebooks

`collect()` / `toPandas()` pulls an unbounded DataFrame into driver memory.

## Why is this a problem?

Spark keeps data distributed across executors. `collect()` and `toPandas()` copy every row into
the memory of a single driver process. On development samples this works; at production
volume the driver runs out of memory and the job fails, often hours into a run. Generated
code frequently collects only to loop over rows in Python, which also throws away Spark's
parallelism.

## What it detects

`.collect()` and `.toPandas()` in files that import `pyspark` or Databricks Connect, and in
Databricks notebooks.

## Example

```python
# Problematic
for row in orders.select("customer_id").distinct().collect():
    process(row["customer_id"])

# Distributed
orders.join(customers, "customer_id").write.saveAsTable("analytics.orders_enriched")

# Bounded on purpose
preview = orders.limit(100).toPandas()
```

## Not flagged

- Chains with `.limit(n)`, also through a variable (`small = df.limit(10)`, then
  `small.collect()`).
- Global aggregates, which always return one row: `df.agg(F.max("ts")).collect()[0][0]`.
  Grouped aggregates (`groupBy(...).agg(...)`) are still flagged.
- `.first()`, `.take(n)`, `.count()`.
- `collect()` on objects in files that are not Spark code.

## Note

Dedicated PySpark performance linters also cover this pattern. It is included because it is
frequent in generated pipeline code.
