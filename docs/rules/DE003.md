# DE003 `hardcoded-date`

**Severity:** warning · **Languages:** SQL, PySpark, Databricks notebooks

A hardcoded date in a filter makes a scheduled job process the wrong window.

## Why is this a problem?

A filter such as `order_date = '2026-01-01'` is correct on the day the query is written and
wrong on every run after it. Scheduled runs keep reprocessing the same day, and backfills
cannot target other days. Nothing fails, so the problem is only noticed when someone asks why
the dashboard stopped changing.

## What it detects

- SQL: date or timestamp literals (`'2026-01-01'`, `DATE '2026-01-01'`,
  `'2026-01-01T08:00:00Z'`, also inside functions such as `to_date(...)`) compared with
  `=`, `<>`, `<`, `>`, `<=`, `>=`, `BETWEEN` or `IN` inside `WHERE`, `JOIN ... ON`, `HAVING`
  or `QUALIFY`. The violation points at the literal itself.
- PySpark: inside `.filter()`, `.where()` and `.between()`: date strings, dates inside SQL
  expression strings (`.where("d >= '2026-01-01'")`), and `date(...)` / `datetime(...)` calls
  with a literal year, month and day.

## Example

```sql
-- Problematic
SELECT * FROM silver.orders WHERE order_date = '2026-01-01';

-- Parameterised by the orchestrator
SELECT * FROM silver.orders WHERE order_date = '{{ ds }}';
```

```python
# Problematic
recent = orders.filter(F.col("order_date") >= "2026-01-01")

# Parameterised
run_date = spark.conf.get("pipeline.run_date")
recent = orders.filter(F.col("order_date") == run_date)
```

## Not flagged

- Sentinel dates: `0001-01-01`, `1900-01-01`, `1970-01-01`, `2999-12-31`, `9999-12-31`
  (common in SCD Type 2 tables).
- Templated values: `'{{ ds }}'`, `'${run_date}'`.
- Dates outside filters: `SELECT` lists, `CASE` expressions in projections, `withColumn`.
- Strings that only look like dates: `'2026-13-01'`, `'2026-01-01-backup'`.
