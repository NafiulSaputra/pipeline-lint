# DE004 `select-star-into-write`

**Severity:** warning · **Languages:** SQL, PySpark, Databricks notebooks

`SELECT *` decides which columns are written to a table.

## Why is this a problem?

With `SELECT *`, the written columns are whatever the upstream table has today. `INSERT`
matches columns by **position**, so when a column is added, removed or reordered upstream,
the load either fails or silently writes values into the wrong columns.
`CREATE TABLE AS SELECT *` copies every upstream change into the new table, including columns
nobody reviewed, such as newly added personal data.

## What it detects

- SQL: `*` or `alias.*` in the final projection of a query feeding `INSERT INTO`,
  `INSERT OVERWRITE` (any branch of a `UNION`), or `CREATE [OR REPLACE] TABLE ... AS`.
- PySpark: `.select("*")` or `.select("alias.*")` whose result is written in the same chain.

## Example

```sql
-- Problematic
INSERT INTO analytics.fct_orders
SELECT * FROM staging.orders;

-- Explicit contract
INSERT INTO analytics.fct_orders (order_id, customer_id, amount, order_date)
SELECT order_id, customer_id, amount, order_date FROM staging.orders;
```

## Not flagged

- `COUNT(*)`, `SELECT *` inside `EXISTS (...)`.
- Subqueries or CTEs whose outer projection is explicit:
  `SELECT a, b FROM (SELECT * FROM s)`.
- Queries that do not write, views, `INSERT ... BY NAME`.
- Delta `MERGE` (`UPDATE SET *`, `INSERT *`) and `MERGE` sources: MERGE matches columns by
  name, not position.

This is the difference from SQLFluff's generic `SELECT *` rule: only stars that decide the
written columns are reported.
